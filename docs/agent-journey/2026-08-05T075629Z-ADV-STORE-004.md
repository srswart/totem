## 3. Advance implemented — complete

**ADV-STORE-004 — Investigation: SurrealDB multi-model one-round-trip spike.**
Complete, with one scope item only partially satisfied (engine parity, §7).

The load-bearing assumption behind G2 and the read → think → write turn model is
**confirmed**: one SurrealQL statement assembles HNSW vector search, graph
traversal, a resolved record link, a temporal cutoff and a scope filter; a turn's
three writes commit or abort as a unit; live queries fire on the embedded engine
and stay silent for rolled-back writes. The two-query fallback the advance
contemplated is not needed.

Five constraints came out of it, written up as TD-002…TD-008 in
`docs/tech-direction/surrealdb.md`. Three are the kind that would have been
expensive to discover later:

- **TD-002** — `<|K,EF|>` engages the HNSW index; `<|K,COSINE|>` silently falls
  back to a full scan **even though the index exists**. Both return correct rows
  on a small table, so only an `EXPLAIN` assertion distinguishes them.
- **TD-004** — a temporal cutoff bound as a `String` rather than a `Datetime`
  raises no error and filters nothing (SurrealQL compares across types by type
  rank). Found because an assertion failed with an extra row, not an error.
- **TD-008** — live notifications are not ordered by statement within a
  transaction. Found because a test flaked ~1 run in 4; see §6.

## 6. The two corrections worth recording

Both were cases where the convenient fix would have destroyed the finding.

**The string cutoff.** The first recall assertion failed with an extra row. The
fast reading is "the expectation is wrong, widen it". The actual cause was that
`$since` had been bound as a `String`, so `created_at > $since` was
constant-true. That became TD-004 and a test that pins the behaviour, because the
same mistake inside a future store query builder would silently widen results —
potentially past a retention boundary.

**The live-feed flake.** After the sentinel rewrite, the live test still failed
about one run in four. The set of notifications was always right; the *order* was
not — `[Create, Update]` and `[Update, Create]` both appeared on the same engine
with the same data. The convenient fix (longer timeout, retry) would have buried
it. It is the engine's behaviour, now TD-008, and it directly constrains the
console: a reducer driven by feed order will be wrong on multi-write turns. The
assertion is now order-insensitive within a transaction and order-sensitive only
across commits; 15 consecutive runs are clean.

An earlier version of the live test also drained the stream until quiet, which
passed in isolation and failed under concurrent load. It now commits a sentinel
record and reads until the sentinel arrives, so proving the *absence* of a
notification no longer depends on a timeout.

## 7. Invariants and scope established only partially

- **Engine parity — partial.** No `surreal` server could be run: the sandbox
  egress proxy refuses `download.surrealdb.com` and `install.surrealdb.com`
  (`CONNECT tunnel failed, response 403`), and the GitHub releases API is not
  enabled for that repository in this session. Building the server from source
  was not attempted. `tests/server_parity.rs` re-runs every experiment over
  WebSocket behind an off-by-default feature; it **compiles but has never
  executed against a server**. Two parity facts were established from SDK source
  and labelled as such: live queries are unsupported over the HTTP protocol, and
  both engines execute through the same `surrealdb_core::kvs::Datastore`.
- **Scope isolation.** The spike proves only that SurrealDB *can* filter scope
  correctly inside the index scan. The invariant that the store *always* does is
  ADV-STORE-001's to establish and test; nothing here enforces it.
- **HNSW recall under selective filters** at realistic corpus size is unmeasured
  — five rows with `ef: 40` cannot distinguish predicate-aware traversal from
  "the graph is small enough that everything is visited". Deferred to
  ADV-STORE-005.
