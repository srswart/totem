# Journey report — ADV-GATEWAY-010 (the browser is a test environment we did not have)

The console now ships inside the gateway image and signs a human in through
AuthKit with PKCE. Everything the suite could check was green before the
first deploy. Then a real person opened a real browser, and two defects
appeared that no in-process test could have reached.

## The two defects, and why the suite was blind to both

**AuthKit's token endpoint cannot be called from a browser.** Its CORS
preflight answers `Access-Control-Allow-Origin: *`, so the browser sends the
POST. The *actual* response omits the header, so the browser completes the
exchange and then refuses to let the page read the result. The token is
minted and discarded. No client-side change repairs a missing response
header, so the exchange now goes through `POST /console/token` on the
gateway's own origin.

That is a deviation from "the gateway is a pure resource server," and the
advance records it as one. It is not the gateway-as-OAuth-client design the
advance rejected: no secret exists, no cookie is issued, no token is minted
here, and the destination comes from server configuration rather than the
request body.

**The console rendered the dashboard while deciding whether it had a
session** — so every load flashed a dashboard before the sign-in card. The
comment beside that code claimed the three-state split existed to prevent
exactly this. Shawn reported the flash; I had written both the code and the
comment that said it could not happen.

Neither is exotic. Both are invisible to a test that calls a handler
in-process or renders a component without a browser — **the same blind spot
that produced the published-schema bug (ADV-GATEWAY-013), the CLI's missing
TLS (ADV-CLI-002), and the dead `json_response` (ADV-GATEWAY-015).** Four
advances in two days, one root cause: this project tests its insides well and
its edges not at all. The console's edge is a browser, and we have no way to
drive one in CI.

## Three identifiers, three deploy cycles

Each mix-up failed in a way that pointed somewhere else:

1. A WorkOS **Application** id is not an OAuth client id. AuthKit's
   authorization server does not know Applications; passing one returns
   `application_not_found`, which reads as "your app is missing" rather than
   "wrong kind of identifier." The working id came from Dynamic Client
   Registration against `/oauth2/register`.
2. The redirect URI is registered with the **client**, not the Application,
   and must match exactly.
3. The RFC 8707 `resource` must match an audience the gateway accepts —
   `https://totem-dev.fly.dev/mcp` here, with the bare origin accepted too
   because the MCP spec permits either. Send the *issuer* instead and AuthKit
   issues a token the gateway correctly refuses, which presents as a login
   failure.

`fly.toml` now carries the DCR call and the Application-vs-client trap in a
comment, because the next person will hit it.

## What was not done, and one thing done badly

**Reviewability 85, Red, not split.** "Serve the console" and "sign a human
in" are separable, and the first is independently deployable. The split was
not considered until the diff was already large. The retroactive argument
that the evidence needs both halves together is true and would still have
been satisfied by merging the serving advance first.

**No preparatory tidy.** The task list asked for one; there was nothing to
tidy, and the evidence box stays unchecked rather than being satisfied by an
empty commit.

**TDD claimed for half the work.** The serving tests were genuinely red
first. The PKCE helpers were tested alongside the implementation. The record
says which is which.

**One deploy was lost to a shell mistake of mine**: a `cd` into the console
crate persisted into the `fly deploy` in the same command, so fly looked for
a Dockerfile in a directory that has none and reported "app does not have a
Dockerfile or buildpacks configured" — a message that invites you to go
inspect your fly config rather than your working directory.

## Still open

`login:executed` is **unchecked** and the advance is **in_progress**. A
sign-in reached AuthKit, authenticated through Google, and came back — which
is exactly what surfaced both defects — but failed at the exchange. That is
not a completed sign-in, and this advance exists for the completed one.
