("Metering episodic reads belongs in the access log (ADV-GATEWAY-001)") confirmed the access log
did not exist yet and was this advance's job to build, not merely wire up.

Design decision worth recording: the access log's **persistence** (schema, repository) lives in
`totem-store` — consistent with the project's "store enforces invariants, not an application
courtesy" pattern used everywhere else — while the **decision of when to write an entry** (which
endpoint, whose claimed identity) lives in the gateway, since that is gateway-specific context the
store has no way to know. A future MCP surface (ADV-GATEWAY-002) or curator job would call the
same `store.access_log().record(...)` the gateway does, not duplicate the table.

advance's Evidence section as "confirmed by an isolated compile check" rather than claimed as an
in-sequence red run, since it wasn't watched fail *before* the implementation was written, only
reconstructed afterward.

### A gap found and named, not silently fixed or hidden

While implementing `handlers::save`, noticed that `store.access_log().record(...)` only runs
*after* `memories().save(...)` succeeds — so a `/save` refused with `StoreError::ScopeDenied` (a
claimed actor writing outside its own claimed scope chain) is never logged. CLAUDE.md's
unlogged-access hazard explicitly calls for checking error paths, not just the happy path, so this
is exactly the kind of gap that instruction exists to catch. Given the advance was already
Red-scored (105) on size, expanding scope to also log refused writes felt like the wrong call this
run — logging a failed access convincingly (what identity, what attempted scope, distinguishing it
from a successful one downstream) deserved its own reviewed slice rather than riding along
un-scrutinized in an already-large diff. Documented plainly in the advance's Risk + Rollback and
"Partially established invariants" sections instead of silently narrowing scope or leaving it
unmentioned.
