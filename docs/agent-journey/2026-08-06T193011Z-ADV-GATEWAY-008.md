## What was built

Two library modules in `totem-gateway`, both new: `eval::workload`
(a workload driver replaying a recall/save mix through `ops::recall` /
`ops::save` — the same functions both REST and MCP call — with bounded
concurrency, latency percentiles, and an environment stamp) and
`eval::quality` (a recall-quality scorer running
`totem_store::corpus::golden_queries()` with an overridable reader chain,
reporting `precision_at_1` / `recall_at_k`). Both are proven sensitive by
dedicated positive/negative control tests: the workload driver's negative
control injects a deterministic per-operation delay and asserts every
latency figure visibly worsens and throughput drops; the quality scorer's
negative control substitutes a reader with no visibility into the corpus's
project scope and asserts both metrics collapse to exactly `0.0`.

Commit series: `test:` (both test files, committed before `src/eval/`
existed — confirmed failing with `E0433: could not find eval in
totem_gateway`, the real reason) → `feat:` (the two modules + `lib.rs`
wiring, makes the tests pass) → `tidy:` (a `cargo fmt` reflow the two
prior commits needed) → `docs:` × 2 (advance record, then the sub-PR link
once the PR existed).

## Corrections made to the advance

Recorded in the advance body's `## Corrections to the Advance` section,
following the precedent ADV-STORE-005 set:

1. **"One command" is a library call, not a terminal command**, for both
   the workload driver and the quality scorer. The declared immediate
   consumers (ADV-CORE-005, ADV-GATEWAY-006, ADV-GATEWAY-007) are all Rust
   code that calls this module directly, so a CLI wrapper was deliberately
   not built — a small future addition, not a discovered gap.
2. **The workload driver measures the shared `ops` layer, not either
   transport separately**, even though the Objective says "recall/save
   mixes over MCP and REST". `ops.rs`'s own doc comment establishes that
   both surfaces call exactly these two functions with no scope-relevant
   logic of their own, so one measurement is representative of both;
   HTTP/MCP marshalling overhead itself is out of scope for this harness.

Neither correction narrows what the advance's Outcome actually needs
(sensitivity-proven latency/throughput reporting and sensitivity-proven
quality scoring) — both are stated plainly rather than silently narrowed.
