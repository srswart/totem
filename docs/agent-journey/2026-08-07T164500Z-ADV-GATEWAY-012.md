# Journey report — ADV-GATEWAY-012

Workstation session, claim-first. Credentials now survive the restart a
deploy performs: schema v10, a fingerprint-only `CredentialRepository`,
start-up loading into the verifying registry, and the bootstrap credential
persisted like any other.

## Scope narrowed, deliberately and visibly

The advance's Behavioral Change promised authenticated issue/list/revoke
**endpoints**. They were not built. The durable layer they need is complete;
the HTTP surface is deferred to ADV-CLI-002, which is their only consumer,
because an admin-privileged surface deserves the adversarial test treatment
ADV-GATEWAY-003 got rather than being tacked on untested at the end of
another advance. Recorded in the advance's own words, not silently dropped —
and the rotation runbook says plainly which step still has no one-command
answer.

## Findings

- **Two SurrealDB 3 syntax traps**, both now commented in the code rather
  than left for rediscovery: record-id interpolation (`table:⟨$var⟩`) does
  not bind — two records silently collapsed into one — and `type::thing`
  does not exist in this version. Rows are written by field against a UNIQUE
  index instead, which is simpler anyway.
- **A message that became a lie.** The fail-closed "no credential is
  registered" warning fired unconditionally on an absent bootstrap. After
  this advance the registry may already hold durable grants, so the warning
  told an operator their credentials were gone while the gateway was serving
  them. Caught by reading the durability test's own output rather than by a
  test — worth noting that the executed evidence, not the assertions, is what
  surfaced it.

## Evidence

Durability was demonstrated against a real on-disk store, not asserted: run
one seeded from the environment; run two started with **no bootstrap
variables at all**, logged `loaded 1 durable credential(s)`, and
authenticated the original token with 200.
