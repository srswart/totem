## What was built

New `totem-cli` crate (binary `totem`, clap-based):

- `totem enroll --repo-root <path> --gateway-url <url> [--source <label>]
  [--no-hook]`: parses `/arrive/` locally via
  `totem_arrive_sync::read_repo_artifacts`, POSTs the resulting
  `LandscapeSnapshot` to a new gateway endpoint `POST /enroll`
  (`totem-gateway`), which calls `totem-store`'s
  `LandscapeRepository::sync` directly. Installs a `post-commit` git hook
  that re-invokes `totem enroll`, refusing to overwrite a hook it did not
  itself install.
- `totem credential create --repo <owner/name> --scope <scope> --actor <id>`:
  issues an opaque token bound to exactly one repo/scope/actor, validated
  with `totem-core`'s own `RepoId`/`ActorId`/`Scope` parsers, refused on a
  scope/repo or scope/actor mismatch. Stored locally
  (`~/.totem/credentials.json` or `$TOTEM_HOME`), `0600` on unix.

Gateway addition: `POST /enroll` route, `EnrollRequest` (flattens
`totem_store::LandscapeSnapshot`, which the `tidy:` commit made
`Deserialize`) / `EnrollResponse` DTOs.

## Scope correction

The advance's Objective, as originally written, implies a *verified*
least-privilege credential. ADV-GATEWAY-003 ("Streamable-HTTP MCP + auth for
cloud agents", `MODEL: claude-opus-5`, security-critical) owns real
gateway-side token verification and is still `status: planned` — this
Sonnet-only run cannot implement it (the model gate applies everywhere, not
just to the advance a routine targets directly). `totem credential create`
therefore issues the *shape* of a least-privilege credential — validated,
repo+scope+actor-bound, stored with restrictive permissions — and this is
recorded plainly in the advance's Objective, Behavioral Change, and Risk +
Rollback sections rather than silently narrowed. The gateway does not check
any token on any request today; this is unchanged by this advance, not a
regression it introduces (`/save`/`/recall` already accepted a
caller-asserted identity before this run).
