## 3. What was built

Promotion is the one sanctioned path across a scope boundary, so the shape of
the work was decided by that rather than by convenience.

**Policy grounded in an existing rule, not a new one.** `PromotionPolicy::path`
reads the category's own `ReviewPolicy` instead of carrying a second
per-category table. Knowledge/Identity/Context auto-promote,
Instructions/Uncertainty gate. A second table would have let a category be
human-gated for review and quietly automatic for sharing — the kind of drift
that compiles and passes review.

**Episodic is `Forbidden`, not `HumanGated`.** Migration 1's `EVENT` refuses
`UPDATE` on an episodic row outright, so a scope change is impossible rather
than gated. Modelling it as gated would have created a queue entry nobody could
ever action.

**Events, not a mutable request row.** A `promotion_event` table, append-only at
the database level with required provenance, matching the pattern `access_log`
and `sync_run` already set. The pending queue is derived (proposals with no
decision referencing them) rather than stored as state.

**Ordering is store-assigned.** `provenance.created_at` is caller-supplied, so
ordering the trail by it would let a wrong or backdated clock rearrange the
record of who decided what. Events carry a `recorded_at` the store stamps,
offset by position within a batch so a proposal and the auto-approval recorded
alongside it have a total order rather than a tie.

**The move and its event are one transaction.** `UPDATE` matching zero rows is
not an error in SurrealQL, which is a real hazard here: without a guard, a
record whose scope had drifted since it was read would leave behind an event
asserting a promotion that never happened. `apply` throws unless exactly one row
moved.

## 4. The design decision worth arguing about

`proposed_record` returns a record the caller's own `ScopeChain` does not reach.
That is the only such path in the crate, and it was not obvious it should exist.

The alternative was to leave it out: `pending()` returns events carrying scope,
category, provenance, and reason but no body, so a reviewer would approve a
private note without reading it. That is a *worse* security posture, not a
better one — it makes the human gate ceremonial. Proposing a note for a wider
scope is, definitionally, asking that scope's reviewers to read it.

So it exists, bounded on four sides: the proposal must still be open, the
reviewer must be able to reach the scope it targets, the fetch is pinned to both
the id and the origin scope the proposal itself recorded (so no other row is
reachable through it), and it returns `None` the moment the proposal is decided.
It is called out under `## Security Notes` in the advance rather than left for a
reviewer to discover.

The related asymmetry: an approver moving ada's record out of `actor:ada` is
authorised by ada's proposal, not by the approver's own reach. The effecting
`UPDATE` therefore pins on `scope = $from` rather than the approver's chain —
using the chain would make approval impossible in the exact case promotion
exists for. This is why propose-time checking is strict.

## 5. Mutation testing

The protocol warns that a test passing against a deliberately broken
implementation is worse than no test. Four guards were removed in turn:

| Guard removed | Tests that failed | Caught? |
| --- | --- | --- |
| `to_scope IN $scopes` in `open_proposal` | `nobody_can_decide_a_proposal_aimed_at_a_scope_they_cannot_reach`, `a_reviewer_reads_the_record_a_pending_proposal_names_and_nothing_else` | yes |
| proposer's target-reachability check | `nobody_can_propose_into_a_scope_they_cannot_reach` | yes |
| already-decided check | `a_decided_proposal_cannot_be_decided_again`, `a_reviewer_reads_...` | yes |
| `IF array::len($moved) != 1 { THROW ... }` | `an_event_is_never_recorded_for_a_move_that_did_not_happen`, `the_transaction_refuses_an_episodic_move_the_policy_would_have_caught_first` | yes |

The fourth is the interesting one. The transaction guard is unreachable through
the public API — `propose` and `demote` both refuse in Rust first — so it would
have shipped untested precisely *because* the first refusal works. Two in-crate
tests call `apply` directly to reach it.

## 8. Stated plainly: what was not achieved

- **Promotion writes no access-log entry.** Consistent with where the store logs
  today — it doesn't; `save` and `recall` log at the surface per
  ADV-GATEWAY-001 — and promotion has no surface yet. When one exposes it
  (ADV-CONSOLE-002 or a gateway advance) an entry must be appended, which needs
  a new `AccessOperation` variant plus a migration widening the `operation`
  assertion, the same shape as migration 4's `feedback`. The promotion trail is
  itself append-only with full provenance, so promotion is auditable now; the
  gap is the who-asked-when record of the triggering request.
- **`governance.review` is untouched by promotion.** Approving a promotion
  decides where a record lives, not whether its content is trusted. Conflating
  them would let a promotion approval silently discharge a content review nobody
  performed. If the console wants one action to do both, that is a product
  decision to make explicitly.
- **Concurrent decisions are not serialised by a lock.** The already-decided
  check reads before it writes. Bounded — the second `apply` finds
  `scope = $from` no longer true and throws, so the outcome is one move plus one
  spurious error rather than two moves — but genuine serialisation needs a
  uniqueness constraint on `proposal`.
- **`ci:passed` not claimed.** CI runs on `advance/**` pushes so a real result
  exists for this branch; this run did not read it.
- Two tests are not red-green pairs and are labelled as such in the advance:
  `the_database_refuses_a_scope_edit_on_an_episodic_row` already passed against
  migration 1, and the two transaction-guard tests were written alongside the
  statement they cover — their evidence is the mutation run, not authoring order.
