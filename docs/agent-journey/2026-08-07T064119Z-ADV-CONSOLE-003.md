## What was built

- `totem-store`: `LandscapeRepository::watch()` — merges one `LIVE SELECT` per landscape table (`repo`/`system`/`component`/`advance`) into a single payload-free pulse stream (`LandscapeChanges`), the trigger the relay wakes on.
- `totem-gateway`: `GET /landscape/:repo/events` — authorizes exactly like the existing `GET /landscape/:repo` (extracted their shared `git_repo` resolution as a tidy step), sends the current view immediately on connect, and a fresh view on every `watch()` pulse. Every emitted view is a fresh, store-enforced `landscape().view()` read and is logged (`AccessOperation::Recall`) — no unlogged access path. The relay lives entirely inside the response body's own `async_stream::stream!` generator, so a disconnected client tears the subscription down for free with no spawned background task to leak.
- `totem-console`: `view_model::parse_landscape_event` (thin delegation to `parse_landscape`, proven identical by test) and `api::subscribe_landscape_events` (wasm32-only, `gloo_net`'s `EventSource`), wired into `RootApp` via `use_future` keyed on `repo` so a repo change cancels the old subscription and opens a new one. The manual Refresh button remains a working fallback and is still the only update path for memories/promotions/uncertainty.

## Corrections made to the advance

- **Scope corrected, recorded honestly rather than silently narrowed.** The advance as originally authored named both landscape *and* memory-table live relay in its Behavioral Change. Only the landscape relay shipped. The memory relay needs per-subscriber `ScopeChain` filtering (materially more work than the landscape relay, which has no per-caller scope filter at all — only the repo binding `authorize_repo` already checks), and bundling both risked either shipping the memory relay hastily on a security-critical surface or blocking landscape on it. Recorded as a Scope correction section in the advance body, with the memory relay left for a follow-up advance.
- Documented, not fixed this run: the live-query trigger is deliberately unfiltered by repo at the SurrealDB layer (a live query cannot dereference `component.system.repo`/`advance.system.repo`, so a repo-scoped server-side filter is not reliably expressible today). Safe because the pulse carries no data — every subscriber re-reads through the store-enforced `view()` — but it means every enrolled repo's changes wake every subscriber's relay to re-check, which will not scale past a handful of concurrently-watched repos.
