### Design decision: shared `ops` module, not two implementations

`handlers.rs` inlined "resolve the scope chain → do the store operation → append one access-log
entry" directly in each Axum handler. Rather than reimplement that sequence a second time for MCP
tool dispatch, extracted it into transport-agnostic `ops::save`/`ops::recall` functions
parameterized by an `endpoint: &str` label (`/save`/`/recall` for REST, `mcp:totem_save`/
`mcp:totem_recall` for MCP) so an audit query can distinguish surfaces without the access log's
"every read and write is logged" claim splitting into two code paths that could drift apart. This
was the `tidy:` commit — pure extraction, no behavior change, confirmed by the pre-existing 8 REST
integration tests passing unchanged before and after.

### Design decision: plain-JSON tool parameters, not `totem-core` types directly

`totem-core`'s own types (`ActorId`, `Scope`, `Harness`, ...) have hand-written `Deserialize` impls
with real validation, which is exactly why the REST DTOs (`dto.rs`) use them directly — a caller
gets `totem-core`'s own rejection of an empty actor id or a malformed scope string, not a second
copy of that rule. MCP's tool input schema, though, comes from `schemars::JsonSchema`, which none
of those types implement, and adding it there would be a `core`-component change outside this
advance's declared scope (`components: ["gateway"]`). Resolved by typing MCP parameters as plain
JSON primitives (`String`, `Option<String>`, `serde_json::Value` for the two enum-shaped fields
`author`/`harness`) and parsing every field through `totem-core`'s own fallible constructors
(`ActorId::new`, `Scope::from_str`, `serde_json::from_value::<Harness>`/`<Author>`, which invokes
`totem-core`'s own `Deserialize` impl) before it reaches `ops`. Recorded as an explicit risk in the
advance rather than silently accepted: a future advance wanting a self-describing MCP schema would
need `totem-core` to grow `schemars` support behind a feature flag.

### Design decision: `totem_landscape` ships real but honestly empty

The objective names `totem_landscape` as part of "the initial tool surface" alongside
`totem_recall`/`totem_save`. `ADV-ARRIVE-SYNC-001` — the advance that would populate real landscape
data — has not landed, and `totem-store` has no landscape repository to query. Rather than omit the
tool (shipping 2 of 3 advertised tools) or fabricate placeholder graph data, `totem_landscape` is
implemented, callable, and schema-correct, but always returns
`{"systems": [], "components": [], "advances": [], "note": "..."}` where the note names
`ADV-ARRIVE-SYNC-001` as why. Covered by its own test
(`totem_landscape_is_callable_and_honestly_reports_no_data_yet`).

### A design difference from REST worth naming explicitly

REST's `error.rs` maps a scope-denied write to `403 Forbidden` with a JSON error body — the caller
still gets a normal, parseable HTTP response. MCP's idiom is different: returning
`Result<T, rmcp::ErrorData>::Err(...)` from a `#[tool]` method surfaces as a **protocol-level**
JSON-RPC error (confirmed by tracing rmcp's `IntoCallToolResult` impls: `ErrorData`'s own impl
returns `Err(self)`, which propagates through the blanket `Result<T, E>` impl rather than being
wrapped into a `CallToolResult { is_error: true }`). `writing_into_another_actors_scope_over_mcp_is_refused`
asserts `result.is_err()` on the `call_tool` future itself for exactly this reason. Documented in
the advance's CFU rather than silently treated as equivalent to REST's behavior.
